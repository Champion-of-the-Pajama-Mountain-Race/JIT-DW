# JIT-DW：开发者十分钟实践指南

**这是一份可以独立阅读的中文快速指南。** 英文[完整 Guide](README.md)提供更细的解释与真实案例。JIT-DW 不负责批准你的代码，不要求安装检查器，也不要求每次提交都改文档。

## 1. 先找读者，而不是先找模板

写文档之前，先想：“谁在做什么事时遇到了困难？”

例如：新成员找不到一个模块的入口；API 的错误条件让调用者误解；运维无法判断一次恢复操作是否成功。针对这些问题，一句话、一段可运行示例、一条链接，可能比新建十份文档更有效。

**如果没有明确的读者问题，不必为了填补目录而写文档。**

## 2. 选择最自然的位置

| 读者需要 | 通常可以从哪里解决 |
|---|---|
| 了解项目并第一次运行 | 根 README、Quickstart |
| 完成特定操作 | How-to / 操作指南 |
| 理解某个概念或架构原因 | Explanation / 概念说明 |
| 查接口参数、错误、配置 | API 注释、生成参考或 Reference |
| 定位模块边界 | 简短的目录 README 或模块说明 |
| 理解一个不明显的实现原因 | 源码附近的 why-comment |
| 追溯过去为什么这样设计 | ADR、历史设计记录；不是当前实现说明 |
| 处理真实故障 | 可验证的 Runbook |

这个表是帮助你选择的菜单，不是必须创建的文件清单。

## 3. 优先让代码更清楚，而不是用注释掩盖问题

例如：

~~~rust
// 示例 API；不是某个项目的实际接口。
set_retry_policy(false);
~~~

你可以增加参数提示：

~~~rust
set_retry_policy(/*enabled*/ false);
~~~

但如果兼容性允许，把参数变成明确的类型可能更好：

~~~rust
set_retry_policy(RetryPolicy::Disabled);
~~~

Codex 的[参数注释工具说明](https://github.com/openai/codex/blob/67f0994b532b8740f14b5b738af7b7b2a915b1d6/tools/argument-comment-lint/README.md)就主张先考虑让 API 自解释，再用必要的注释补充。**代码实现者对是否能安全改 API 最有发言权。**

## 4. 一个好的最小文档，能把读者带到结果

如果是快速上手页，通常回答：

- 我可以用它做什么？
- 运行前需要哪些条件？
- 输入哪条**实际可运行**的命令？
- 正确时应该看到什么？
- 失败后如何定位，下一步去哪里？

Rust 的 [rustdoc 写作指南](https://github.com/rust-lang/rust/blob/92b5b8c87c61b20adc9001b41baf587634a74734/src/doc/rustdoc/src/how-to-write-documentation.md)强调模块定位与可用示例；Django 的[文档写作指南](https://github.com/django/django/blob/f4c65fd6a517dd32bd2e732ae3543e550e56f206/docs/internals/contributing/writing-documentation.txt)强调教程、操作、概念与参考承担不同的阅读任务。

参考一份[有完整命令与预期结果的教学示例](recipes/first-success.md)。

## 5. 修改代码时，顺手问一句“什么知识变了？”

可以在脑中完成，不要求写审批记录。

- 只是实现内部优化，公开行为没有变化？可能什么都不用写。
- API 的默认值或报错变了？也许应该修改接口说明或现有示例。
- 改了 UI 提示文案？提示文本本身就是读者会看到的信息，不必机械地增加 Markdown。
- 改了 Schema 或自动生成的 SDK？使用项目已有的生成与检查机制。
- 改了被程序**解析**的 docstring？它可能等同于修改接口行为，应检查解析结果和测试。

别把“没更新文件”自动当成失败，也别为了通过检查器而编造无用文档。

## 6. 什么时候可以停？

当读者能够找到入口、完成任务、理解重要限制，并知道接下来去哪里时，通常就够了。

**不要用文件数、注释行数或 CI 绿灯代替读者体验。**

对于巨大且历史材料丰富的项目，最好的改善未必是大规模重写：试着从 README 找到一个模块，读源码旁的接口说明，必要时再进入规范与历史记录。我们计划在[第一个私有项目的可用性试点](../validation/pilots/first-private-pilot.md)中采用这个方式；具体源码和任务记录只保留在该项目的私有工作区。

## 三个你可以放心作出的决定

- “当前 README 已经够用，没有必要另建目录文档。”
- “这里的注释只是重复代码，我先改一个更清楚的名字。”
- “这个接口会被别人调用，错误行为值得明确说明；可以写一条简短示例。”

只要能解释它怎样帮助项目和读者，这些都可以是好的文档决策。
